Making my Issue-Tracker

How the API issue tracker came together — modelling issues, routes, and the bits I'd redo.

This started as coursework and turned into the project I actually reach for. It is a REST API for tracking the bugs inside a codebase — the ones that go quiet in a chat thread and never come back. There is a running copy deployed on Cloud Run.

The problem

Every project I have worked on fails the same way: something breaks, someone notices, and by the time anyone goes looking the context is gone — who hit it, how to reproduce it, whether it was ever fixed.

So the design goal was narrow: one issue should be enough on its own. No "see the thread", no "ask the person who found it". If a single document does not tell you what is wrong and what to do next, the tracker has already failed.

Modelling an issue

One issue is most of the design. The shape I settled on:

{
  "title": "Dark mode drops websocket messages when suspended",
  "description": "…",
  "status": "open",
  "priority": "high",
  "stepsToReproduce": "1. Create a test account…\n2. Trigger the action twice…",
  "classification": "unclassified",
  "author": { "userId": "…", "fullName": "…" },
  "assignedTo": { "userId": "…", "fullName": "…" },
  "createdOn": "…",
  "comments": [],
  "testCases": [],
  "timeLog": []
}

Status (open/in-progress/closed) answers where is the work. Priority (low/medium/high) answers how soon. Classification (unclassified/approved/unapproved/duplicate) answers is this even real. Comments, test cases and time logs are embedded arrays — one document, one read, no joins.

Fields worth keeping

  • stepsToReproduce as one string, not an array. In the repo it is a single free-text field. A numbered block pasted into one string is easier to write and read than structured steps, and nothing downstream needs the structure.
  • classification separate from status. Keeping triage and progress apart stopped me conflating "we decided this is a duplicate" with "the work is done".
  • Embedded sub-resources. Comments, test cases and time entries live inside the issue document. The trade is that sub-resource writes go through $push/$pull and, for a single test case, an arrayFilters update — but reads stay a single lookup.
  • { userId, fullName } snapshots. Author and assignee carry their display name with them, so rendering an issue never depends on another service being up.

The API surface

Fifteen endpoints under /issues, plus a /health. Listing them is the fastest way to see the shape of the thing: 

GET    /issues                             list; ?q= searches titles and descriptions
GET    /issues/:id                         one issue
POST   /issues                             create
PATCH  /issues/:id                         partial update
PATCH  /issues/:id/status                  open | in-progress | closed
PATCH  /issues/:id/classify                unclassified | approved | unapproved | duplicate
PATCH  /issues/:id/assign                  { userId, fullName }
DELETE /issues/:id

POST   /issues/:id/comments                add
PATCH  /issues/:id/comments/:commentId     edit
DELETE /issues/:id/comments/:commentId     remove

POST   /issues/:id/test-cases              add
PATCH  /issues/:id/test-cases/:testCaseId  { passed }

POST   /issues/:id/time-log                { hoursWorked }
GET    /issues/:id/time-log/summary        total hours for one issue

Status, classification and assignment get their own verbs instead of riding on the general PATCH. It reads better — a client setting a status is saying something narrower than "update this" — and each transition gets a schema of its own rather than one loose partial.

Validation at the edge

Nothing reaches a controller unparsed. Every route that takes input runs it through a Zod schema first — validateBody, validateQuery or validateParams — which parses the value and replaces it on the request, so a handler only ever sees data that already typechecks. A failure short-circuits with a 400 that names the field that failed: 

{
  "error": "ValidationFailed",
  "details": [
    { "path": "status",
      "message": "Invalid option: expected one of \"open\"|\"in-progress\"|\"closed\"" }
  ]
}

Two details in there are worth copying. The list route's query is validated like a body, so ?status=done is a 400 instead of a silent empty result — and page and limit come out of that same schema already coerced to numbers and capped at 50. And updateIssueSchema is the create schema made partial, plus a refinement that rejects an empty object, so PATCH cannot be used to send nothing and still get a 200.

Who is writing

The routes that create something — an issue, a comment, a test case, a time entry — carry an attachCurrentUser middleware. Author and commenter come from the request and never from the body, so an author field in the JSON is ignored, which is the only reason the embedded { userId, fullName } snapshots can be trusted at all. Today that middleware is a stub handing back one hardcoded user. It is the seam where real authentication goes.

What I'd do differently

  • The routes → controllers → data seam is right, but the controllers still do too much. createIssue calls insertIssue without awaiting it and responds with the object it built rather than the inserted document. updateIssueById builds an ObjectId without the isValid guard the other data functions use, so a malformed id throws instead of returning a 404.
  • The id field lies about its type. It is derived from _id with a cast that ends in as unknown as number — a string wearing a number's clothes. I would fix the type and drop the cast.
  • Naming drifted. stepsToReproduce, createdOn, assignedTo — I would pick one convention and hold it across the schema.
  • Half-finished fields. timeLog exists with no endpoints, and a FixInfo type sits commented out. Either finish them or delete them.
  • Splitting app.ts from index.ts was the best late call. It let the tests run without a live Atlas cluster. I would do it on day one next time.
